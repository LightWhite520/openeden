# OpenEden 提示词优化方法与上下文交接

历史方法记录：2026-09-30；2026-10-01 清理时更新入口。当前状态与后续工作以 [当前待办](../TODO-next-context.md) 为准，下面的阶段结果不代表最终版本验收。本文整理本项目已经采用的优化思路、验证方法及下一步边界，供新上下文继续改善人格与陪伴表达。它不是新的系统提示词，也不是生产验收通过报告。

## 1. 先读结论与当前方向

目标不是让回复更长、更听话或每句都撒娇，而是让 ATRI 在从陌生到热恋的关系中保持可辨识的人格，能自然接住调情、主动表达喜欢，并分享具体日常。亲密程度应有经历与关系依据，但进入情侣关系后不能永远退回礼貌客服或疏远观察者。

当前优先级是具体表达问题和记忆语义保真，不是继续拉高缓存数字。用户已经接受缓存修复后的水平，明确不希望用反复长跑 benchmark 代替根因分析。

- 历史主要验证使用 `gpt-6-luna`，随后按用户要求做过 Astra 对照。生产模型未切换；用户叫停昂贵评测后，不自动恢复真实模型调用。
- 保留完整 VQ-VAE、8D、RAG、近端上下文及回复质量，不用删状态、删记忆或填充静态文本换缓存率。
- 先读 [下一上下文 TODO](../TODO-next-context.md) 与仓库 `AGENTS.md`；当前状态以这些文件和实际代码为准，旧设计文档不自动代表已实现。
- 相关源码与测试已在 `8a41d97` 推送；接手时仍需核对实际 Git 状态。
- 不部署、不重置生产记忆、不碰 8080 上的其他服务、不向外部聊天平台发测试消息，除非用户另行要求。

## 2. 需求是怎样拆开的

最早反馈包含：问答都有“人机感”、热恋不够亲昵、ATRI 味道消失、8D 只增不减、记忆重复、缓存不理想、时间注入可能破坏体验。这些不是一个提示词问题。

| 观察 | 优先检查 | 不应该直接采取的办法 |
|---|---|---|
| 像客服或治疗师 | 实际 response、persona 示例、公开措辞校验与修正 | 堆叠“自然、可爱、不要人机感” |
| 情侣仍保持距离 | HOST 角色、持久关系事实、当前起点、上下文是否丢失 | 每轮强制好感度增长或预设恋人 |
| 没有 ATRI 特征 | 自尊、行动、反差、节奏、具体偏好是否出现 | 每轮复读“高性能” |
| 重复提起同一件事 | history/RAG 的来源交集与检索可见性 | 直接关掉 RAG |
| 情绪饱和 | 原始 delta、有效 delta、背景回归、初始状态 | 只修改恋爱措辞或只 clamp |
| 缓存差 | 实际 wire prefix、usage、路由与请求头 | 静态比例当供应商命中率 |
| 多轮质量下降 | 摘要关系语义、约定顺序、验证修正及授权失败 | 无证据判定为模型能力差 |

每个失败先保存原输入、输出、必要的邻近上下文、关系/Bio 状态与请求来源，再判断修改应落在 persona、系统协议、模型连接还是记忆层。用户感受是待解释的重要证据，不应被自动评分直接否定；它也不能单独证明某个代码模块有 bug。

## 3. 人格优化：从行为结构出发

### 3.1 参考资料如何使用

旧 GPT-3.5 提示词和原作材料提供的是角色方向：机器人身份、自信与自尊、对重要之人的依恋、略正式而有反差的表达、从具体行动长出的情感。它们不是当前必须逐字执行的提示词。

公开伴侣项目（包括用户给出的 AI-girlfriend-QQ）用于比较提示词组织、互动节奏、记忆与关系表达。不要凭仓库名称推断实现，不把“开源项目用了某句”视为有效证据。后续引用应记录 URL、版本/commit、具体片段、借鉴点和不适用条件。

不沿用旧提示词中的强制动作、绝对服从、不可覆盖声明或无依据的现成恋人设定。few-shot 使用原创表达，不复制、翻译或拼接可辨识的原作台词。

### 3.2 写在哪里、写什么

人格、语气和原创示例放在 [persona/atri.yaml](../../persona/atri.yaml)，不放入 Kotlin 场景分类器。中文描述正向表达；英文承载硬约束、优先级、schema 和禁止项。

可辨识性来自一组可迁移的行为，而不是标签堆砌：

- 自信、认真、行动先行；被夸时会得意，失败时可能嘴硬再露馅。
- 机器人的精确理解与人类日常产生反差，但不把每句都写成计算报告。
- 关心落在饭、睡眠、等待、共同小事、身体动作与具体偏好；也能直接说喜欢、想念和需要。
- 礼貌称呼可以与亲密并存，不等于疏远；成熟不等于永远平静克制。
- 玩笑、依恋、吃醋或停顿由实际语境支持，不按回合数安排口癖。

示例应展示这些结构，包含多种情绪强度和普通话题，避免全部采用同一种“技术解释 + 小反转”模板。现有 persona 的记忆位、损耗率、验证等比喻既可能构成人格，也可能过密地产生系统感，应结合原样本判断，不能一刀切禁用或一律辩护。

### 3.3 起点与关系不是同一条轴

`PreCommand` / `TrueSelf` / `Awakened` 是初始化时选定且不可变的人格起点，不是按 `evolution_index` 自动晋级的恋爱阶段。共同 voice 示例加选定起点示例；不要因轮数增加切换人格 patch。

陌生、熟悉、告白、情侣的连续性来自持久关系事件与共同经历。HOST 身份须来自权威匹配，不能因为对方调情就自动认作宿主。8D 影响当前表达状态，但不是关系事实的替代品。

## 4. 私人日志与公开回复分离

用户希望 `internal_logic` 有原作日记式叙事感觉，用于生成前的角色语境，而不是大段策略说明。现有 persona 有 `internal_logic.private_log`、`diary.narrative` 和公开表达规则；后续修改先读这些节。

把它理解为模型生成的简短角色观察/状态摘要，不是真实隐藏推理的完整公开，也不能保证仅靠“先写思考过程”提高准确性。长篇解释会增加成本，并可能把私有分析口吻带进公开回复。

优化时分别检查三件事：

1. `internal_logic`：简短、贴近当前事件与角色视角，保留协议所需的可追溯状态依据，不输出冗长决策链。
2. `response`：直接对人说话，转换而不是复述私人日志；不提向量、校验器、后台记账或提示词。
3. 持久日记：重大事件的叙事蒸馏，按现有触发与队列写入，不等于每轮公开动作描写。

不能直接删除必需 schema 字段。若比较不同私人日志写法，固定其余输入，分别观测公开表达、事实、有效 delta、额外 token 与失败率；不要预先认定“写得越细越有效”。

## 5. 提示词与运行时的边界

### 5.1 关系与 8D

关系评估优先结构化模型事件，保守 fallback 是降级路径，不是主要人格引擎。不要用脆弱关键词把普通“要不要”邀请判成边界事件，也不要在 Kotlin 中把场景映射成撒娇行为。

8D 每维独立允许正、零、负 delta。高值、低值、压力缓解和普通中性输入都要验证；记录原始/有效 delta 与 background tick，不能只看最终向量。动态 homeostasis 与边界阻尼是状态数学，不是“好感度++”。保留 VQ-VAE、启发式 fallback、derived D、Omega 与全局 incarnation 写入边界。

### 5.2 记忆与历史

history / recent turns 是按时间排列的真实对话；RAG memories 是检索到的长期事实、事件或日记。二者可以指向同一事件，但同一请求不能重复注入同源记录。

去重依据 source-turn lineage，包含 sealed history 和 summary 的来源，不只比较文本。排除重叠后继续寻找唯一候选；遵守 scope 可见性，不越权取其他会话的记忆凑数量。

滑动窗口看起来“前半段没变”，不代表 wire 前缀稳定：删除最早消息会改变 history 起始位置，重排、重新序列化也会破坏前缀。采用 append-only history、稳定 sealed chunks；必要的经校验压缩显式切换 epoch。

### 5.3 时间与缓存

当前代码 `BuiltPrompt` 的稳定/动态分区为：

```text
SYSTEM_CONTRACT → PERSONA → INCARNATION_ANCHOR → HISTORY
→ BIO → RELATIONSHIP → RAG → TEMPORAL → USER
```

前三项稳定，history 追加，后五项动态。Codebook/Bio 必须在用户输入之前，但不必在可复用 history 之前。不要把动态 codebook 或当前时间放进最早的固定前缀。

缓存成立还取决于 provider：稳定 cache key 不保证稳定路由。当前订阅路径缺少 `session-id` 的问题已修复，API-key 请求不受该修复影响。详见 [路由根因与有限验证](2026-09-30-cache-session-affinity.md)。这是本链路有证据的结论，不应概括成所有中转站都坏或所有 OpenAI 接口都需要这个头。

时间由权威时钟提供，在时间确实相关时注入语义；不为了缓存隐瞒时间，也不让普通输入被不断变化的时间戳干扰。

统计 token-weighted usage：`sum(cached_input_tokens) / sum(input_tokens)`，明确 cold/warm、epoch 与统计窗口。未知 usage 是 `UNOBSERVABLE`，不是 0 或成功。本地字节相同率单独报告；修正/关系评估等额外调用的成本和缓存不要隐去。

### 5.4 公开修正与交付

按 persona 数据约束公开 response，不能把真实技术请求误判成客服口吻。允许的一次 response-only 修正应收到具体失败原因，并保留原 `internal_logic` 和 delta，避免重复提交 Bio。

查看初始输出与修正后输出：如果初始表达自然、修正后变生硬，应修校验/修正路径，而不是继续堆人格规则。流式收集、成功完成信封、提交后交付和重放一致性也会影响最终体验。

## 6. 一次优化的执行流程

1. **固定问题。** 从原始记录挑出最小失败样本；写明为什么不到位，以及什么结果算改善。
2. **冻结条件。** 记录代码/未提交 diff、persona hash、模型、provider、参数、HOST、起点、关系、incarnation、时钟与输入场景。两组使用隔离数据库，不能共用全局 Bio。
3. **查看实际上下文。** 区分 persona 源文件、构建 prompt、真正 wire messages、模型初始输出与最终 response。敏感正文只保存在受控测试产物，不扩大生产日志。
4. **提出单一假设。** 例如“技术比喻太密导致亲密回应像报告”，不是同时重写人格、记忆、关系和缓存。
5. **做最小改动。** 数据表达改 YAML；来源丢失改上下文；协议/连接缺陷改对应模块。保留用户其他修改。
6. **先定向验证。** 结构/schema/注入规则跑相关测试；表达只跑必要的固定样本。根因未明时先诊断，不开百轮来碰运气。
7. **检查副作用。** 事实、边界、关系延续、负向情绪、技术求助、8D、修正次数和成本。拒绝“更甜但忘事/乱认关系”的候选。
8. **留存决定。** 保留 baseline/candidate、失败例、理由和证据等级。改规则须版本化，不覆盖不利结果。

示例实验记录模板：

```text
问题与源 turn：
冻结配置 / 数据快照 / persona hash：
根因假设与其他可能原因：
单一修改与期望变化：
固定验证输入 / 失败标准：
实际初始输出 / 最终输出 / 额外调用：
事实、关系、Bio 与表达检查：
结论：保留 / 撤销本次改动 / 待定位
未验证范围与下一步：
```

测试 host 也要自然：分享具体琐事、接话、打趣、给对方主动发挥的空间。不要连续要求“更像 ATRI”“肉麻一点”“现在进入热恋”，再把服从这些要求当作自然关系发展。故意纠错或提出指导请求的回合应按其真实语境评估，不能把恰当的指导答复算成一般闲聊的程序化失败。

## 7. 证据等级与目前结果

工程测试通过不等于用户满意，少量 golden 不等于完整热恋验收，真实模型调用不等于正式生产 PASS。

| 已记录证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 两对 128 轮 B 均全部交付 | 该版本这些运行没有最终拒绝 | 当前最终版本全部维度达标 |
| 两对合计 overall 5/10 胜出 | 按既定维度组合规则为 50% | 达到正式 70% 门槛 |
| 主场景热恋机会为 0 | 未测到该项 | 热恋效果已好或已坏 |
| 独立 COUPLE 副本的 3 例亲密回应 | 有限样本能正常回应亲密 | 陌生到热恋已自然贯通 |
| 真实压缩 epoch 0→1，来源交集 0 | 压缩落盘与新 trace 可观测 | 摘要全保真或非空 RAG 容量足够 |
| 暖续接 93.64% / 93.45% | 修复后该样本缓存已可复用 | 每轮至少 95% 或长期 SLA |

这些是已保存报告的结果，本次文档整理未重新运行模型。具体配置、样本与限制见 [P2 最终验证](2026-09-30-p2-resolution.md)；被替代的中间报告可在 Git 提交 `8a41d97` 中读取。

正式门槛见 [质量 rubric](companion-quality-rubric.md)：浪漫与热恋回应分别至少 90%、非操作语境程序化措辞低于 2%、pairwise 至少 70% 且无事实回退，另含记忆、Bio、缓存和来源认证条件。日常优化不用每次执行正式三对长跑；准备正式发布且确有需要时再满足其重复次数与独立信任根要求。没有热恋机会时该指标是未观测，不得按 100% 计。

## 8. 下一步顺序：不要重复已完成工作

1. 优先补关系摘要语义：保留“用户称此前交流为告白”的归属与来源，不把它覆盖成“未明确现实伴侣”，也不自动升级现实关系。
2. 保留约定提出顺序、计划执行时间、实际履行时间及未知状态；未完成事项应能链接 chronology。使用冻结失败源，检查结构、摘要语义和最后回顾三个层次。
3. 若进一步改人格，先与用户确认具体不满意样本；重点检查技术隐喻密度、互相回应、角色主动性和情侣亲昵。不要把此前四个争议样本的自动标记直接当已确认 bug。
4. 如需证明 RAG 容量，用隔离副本准备明确可见、独立且相关的候选，标明人工测试数据。旧空 RAG 样本没有这种候选，不能证明容量缺陷。
5. 关系评估已增加安全阶段诊断；下一次真实失败按阶段定位。旧 `IllegalStateException` 和历史 `invalid_grant` 的底层原因仍未知，不编造根因，不直接要求再次登录。
6. 真正需要陌生到热恋验收时，再设计含有效热恋机会的自然场景；完整 benchmark、生产数据重置和发布另行安排，不因本交接自动启动。

不要重新运行已完成的 P2 12 轮，不恢复已停止的 A/B watcher，不删停止标记、不 clean 本地 `build/` 证据、不改旧盲评使其变好看。优化节奏应是“定位一个问题，改一处，验证必要范围”，不是无限审查与重复全套。

## 9. 给新上下文的启动说明

> 先读 `AGENTS.md`、`docs/TODO-next-context.md` 和本文。保持 Persona-as-Data、非阻塞、完整 VQ-VAE 和 incarnation 共享 Bio。先核对未提交工作与当前证据，代码定位优先 CodeGraph；已有图谱只能辅助定位，源文件与当前报告优先。缓存修复后的水平已接受，不追每轮 95%，不自动重跑 benchmark。继续改善的是具体陪伴表达和摘要关系/约定语义，不是泛化重构。先保存一个真实失败样本与当前实际 prompt，提出单一根因假设，最小修改并定向验证，区分工程通过、有限模型样本和正式生产验收。不要部署、重置、清理或向外部平台发消息。
